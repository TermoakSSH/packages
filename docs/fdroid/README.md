# Termoak in the official F-Droid repository (draft)

Termoak already has its own F-Droid repository,
`https://pkg.termoak.com/fdroid/repo` (see the [main README](../../README.md#android-f-droid)).
This folder prepares the inclusion in the main F-Droid repository
(f-droid.org), which builds every app from source itself. Nothing has been
submitted yet.

- [`com.termoak.yml`](com.termoak.yml): the draft of `metadata/com.termoak.yml`
  for [fdroiddata](https://gitlab.com/fdroid/fdroiddata), passes `fdroid lint`
  (fdroidserver 2.4.2; the category names are only valid inside fdroiddata,
  whose `config/categories.yml` defines them).

## How F-Droid would build it

The app is Kotlin/Compose on top of the Rust engine (`termoak-ffi`, UniFFI)
from the `core` submodule (TermoakSSH/core):

1. `submodules: true` checks out `core/` at the commit pinned by the tag
   `android-vX.Y.Z`.
2. rustup from the `rustup` srclib installs the pinned Rust toolchain with the
   `aarch64-linux-android` and `armv7-linux-androideabi` targets, then
   `cargo install --locked cargo-ndk@4.1.2`.
3. `cargo ndk -t arm64-v8a -t armeabi-v7a --platform 26 -o
   bindings/kotlin/src/main/jniLibs build -p termoak-ffi --lib --profile mobile --locked`
   in `core/`, with the NDK given by `ndk:` (30.0.16248370, the one of
   `core/scripts/android-builder.Dockerfile`).
4. The Kotlin bindings (`core/bindings/kotlin/src/main/kotlin/.../termoak_ffi.kt`)
   are committed in core, generated by `scripts/generate-bindings.sh` (the
   `uniffi-bindgen` binary of termoak-ffi, `--features bindgen`). F-Droid can
   use them as they are; to regenerate them in the recipe, add
   `cargo run -p termoak-ffi --features bindgen --bin uniffi-bindgen -- generate --no-format --library <host .so> --language kotlin --out-dir ...`
   after a host build of termoak-ffi, which doubles the Rust build time.
5. `gradle: [yes]` runs `assembleRelease`. Without `keystore.properties` the
   release APKs are unsigned:
   `app/build/outputs/apk/release/app-<abi>-release-unsigned.apk`.

## Before submitting: changes in TermoakSSH/mobile-android and core

- **fastlane metadata** in the app's repository:
  `fastlane/metadata/android/{en-US,es-ES}/{title,short_description,full_description}.txt`,
  `en-US/images/icon.png` and `images/phoneScreenshots/*.png` (copy them from
  `fdroid/metadata/com.termoak/` here) and, optionally,
  `changelogs/<versionCode>.txt` per version.
- **Pinned Rust toolchain**: `core/rust-toolchain.toml` (`channel = "1.99.0"`,
  with the Android targets) and the same version in the builder image, which
  today installs whatever "stable" was when it was built. The recipe's
  `--default-toolchain` must be that version.
- **Path remapping** in the engine: rustc embeds absolute paths (the cargo
  registry, the source directory) in panic messages and in the `.so`, and
  F-Droid builds in `/home/vagrant/build/com.termoak` with its own
  `CARGO_HOME`. Add to `core/.cargo/config.toml` something like
  `[build] rustflags = ["--remap-path-prefix", "...=/cargo", ...]`, or set
  the same `RUSTFLAGS` with `--remap-path-prefix=$CARGO_HOME=/cargo
  --remap-path-prefix=$PWD=/src` in `release-local.sh` and in the recipe.
- **`termoakVersionCode=<base>`** in `gradle.properties` (601 for 0.6.1),
  read by `app/build.gradle.kts` (or checked against the computed one), so
  `fdroid checkupdates` can find new versions (`UpdateCheckData`).
- Push: it stays off in the published APKs. If Firebase Cloud Messaging is
  turned on, F-Droid needs a build without it (a flavor), and its APK would no
  longer match ours: reproducible builds would only work with a matching
  flavor published on GitHub too, or with UnifiedPush.

## Reproducible builds

With `binary:` and `AllowedAPKSigningKeys:
392c208a05fb966c38fa36d3853fb80edd4739d28dfd1d27ea7eba68fc1f4748` (SHA-256
of our signing certificate), F-Droid builds the APK, copies our signature
from the GitHub APK onto it (apksigcopier; ours are signed with APK Signature
Scheme v2) and publishes it only if the result verifies, i.e. if both builds
are byte-for-byte identical apart from the signature. Then users can move
between GitHub, pkg.termoak.com and f-droid.org without reinstalling. Things
that must match:

- Rust toolchain, `cargo-ndk`, NDK (30.0.16248370), `--platform 26`, the
  `mobile` profile (`opt-level = "z"`, fat LTO, `codegen-units = 1`,
  `strip = "symbols"`) and `Cargo.lock` (`--locked`).
- Path remapping (above).
- JDK 17, build-tools 37.0.0, the Gradle wrapper (9.8.0) and AGP 9.4.1: R8
  and the APK packaging are deterministic with the same versions.
- AGP's `META-INF/version-control-info.textproto` holds the git commit: same
  tag on both sides, so it matches; a build from a dirty tree would not.
- Baseline profiles (`assets/dexopt/baseline.prof`) were a known source of
  differences in older AGP versions; check with `diffoscope` if the first
  attempt fails.
- The build environment: build it once with `fdroid build` in the F-Droid
  buildserver image, or with the `registry.gitlab.com/fdroid/docker-executable-fdroidserver`
  image, and compare with `apksigcopier compare` (or `diffoscope`) against
  the GitHub APK before submitting.

If they cannot be made identical, F-Droid signs with its own key: the app is
still accepted, but its installs do not update over GitHub/pkg.termoak.com
ones (different signature) and vice versa.

## Merge request steps

1. Fork https://gitlab.com/fdroid/fdroiddata and clone it; install
   fdroidserver (or use the `docker-executable-fdroidserver` image).
2. Copy `com.termoak.yml` to `metadata/com.termoak.yml`, update the version,
   versionCodes and commit to the latest `android-v*` tag.
3. `fdroid readmeta`, `fdroid rewritemeta com.termoak`,
   `fdroid lint com.termoak`, then `fdroid build -v -l com.termoak` (latest
   version) and fix the recipe until both ABIs build and, ideally, match
   our APKs.
4. `fdroid checkupdates --allow-dirty com.termoak` to see that the update
   check finds the latest tag.
5. Commit ("New app: Termoak") in a branch and open the merge request with
   the "App inclusion" template: describe the app, the license, the
   anti-features (none), the network services (Termoak servers: AGPL,
   self-hostable; AI providers configured on the server with the user's own
   keys) and that reproducible builds are intended
   (`AllowedAPKSigningKeys`).
6. Answer the review (the scanner may ask about JNA's prebuilt
   `libjnidispatch.so` from Maven Central; several apps use the AAR as it
   is, otherwise it can be built from source with a srclib).

Once it is published, the README of pkg.termoak.com can point to f-droid.org
as well; our repository can stay for faster updates (F-Droid builds take a
few days after each tag).
